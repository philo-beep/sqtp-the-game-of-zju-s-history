# 技术组协作说明

## 文件信息

- **文件路径**：`技术组/README.md`
- **文件用途**：作为技术组的总 README，统一说明四名技术成员的职责、代码边界、分支协作方式和交付标准。
- **应阅读人员**：技术组全体成员、项目负责人、内容组接口人和后续参与开发的 Agent。
- **更新时机**：技术架构、分工、接口、目录或 Git 协作规则发生变化时更新。

## 一、项目技术目标

技术组负责搭建一个支持多人自助使用的校史剧本杀微信小程序。用户可以自行创建或加入房间，系统自动完成角色分配、剧情推进、线索发放、答题、投票和结局结算。

技术组的交付目标是：

```text
用户登录
→ 创建或加入房间
→ 自动分配角色
→ 阅读剧情和查看线索
→ 完成任务、答题和投票
→ 系统自动计算结局
→ 保存并展示游戏结果
```

内容组负责提供校史资料、剧本、角色、线索和结局规则；技术组负责把这些内容配置成可运行的多人游戏系统。

## 二、技术组目录与职责

```text
技术组/
├─ README.md                    # 技术组总体协作说明
├─ 01-player-miniapp/           # 成员1：玩家端小程序
├─ 02-admin-web/                # 成员2：内容管理后台
├─ 03-game-engine/              # 成员3：自动游戏引擎
└─ 04-platform-server/          # 成员4：平台后端与云服务
```

四个功能分支与目录对应如下：

| 成员 | 工作目录 | Git 分支 | 主要职责 |
|---|---|---|---|
| 成员1 | `技术组/01-player-miniapp/` | `feature/player-miniapp` | 微信小程序玩家端 |
| 成员2 | `技术组/02-admin-web/` | `feature/admin-web` | 剧本配置和管理后台 |
| 成员3 | `技术组/03-game-engine/` | `feature/game-engine` | 房间状态和自动主持逻辑 |
| 成员4 | `技术组/04-platform-server/` | `feature/platform-server` | 登录、数据库、实时通信和云服务 |

### 成员1：玩家端小程序

负责普通用户使用的微信小程序页面和交互：

- 微信登录和用户信息展示
- 创建房间、加入房间和分享房间
- 房间大厅和玩家状态
- 角色查看
- 公共剧情和私密线索展示
- 任务、答题和投票页面
- 游戏结局和历史记录页面
- WebSocket 状态提示
- 断线后恢复当前游戏状态

不负责游戏规则判断、数据库结构设计和内容审核。页面中的游戏状态必须以服务端返回的数据为准。

### 成员2：内容管理后台

负责内容组使用的管理网页：

- 管理员登录和权限页面
- 剧本创建、编辑、发布和下线
- 角色配置
- 章节配置
- 公共剧情配置
- 私密线索配置
- 任务、答案和投票选项配置
- 结局条件配置
- 房间和游戏记录查看

不负责玩家端页面和核心游戏规则执行。后台提交的数据必须通过表单校验，不能产生缺少必填字段或无法运行的剧本配置。

### 成员3：自动游戏引擎

负责系统自动主持游戏的核心后端逻辑：

- 房间状态机
- 开始游戏的条件判断
- 角色随机分配
- 章节推进
- 线索发放规则
- 答题判断
- 投票结束和结果计算
- 结局条件匹配
- 倒计时和超时处理
- 重复提交和非法操作拦截
- 游戏结束和结果保存流程

不负责微信登录、云服务器配置和管理后台页面。所有核心规则必须在服务端执行，不能只写在小程序前端。

### 成员4：平台后端与云服务

负责支撑整个系统运行的基础服务：

- 微信登录和身份认证
- 用户、房主和管理员权限
- 数据库表结构和基础数据访问
- 用户、房间、剧本和游戏记录接口
- WebSocket 实时通信基础设施
- 玩家断线重连和状态同步基础能力
- 图片、音频等资源上传
- 缓存、日志和错误记录
- 开发环境、测试环境和生产环境部署
- 数据备份、监控和基础安全配置

不负责章节推进、结局计算等具体游戏规则。平台服务为游戏引擎提供稳定的数据和通信能力。

## 三、代码目录建议

项目正式建立代码仓库后，建议采用以下结构：

```text

├─ miniapp/                    # 成员1负责
├─ admin-web/                  # 成员2负责
├─ server/
│  ├─ modules/
│  │  ├─ auth/                 # 成员4
│  │  ├─ users/                # 成员4
│  │  ├─ rooms/                # 成员3、成员4协作
│  │  ├─ scripts/              # 成员4提供数据接口，成员2使用
│  │  ├─ game-engine/          # 成员3
│  │  ├─ answers/              # 成员3
│  │  └─ votes/                # 成员3
│  ├─ websocket/               # 成员4
│  ├─ database/                # 成员4
```

公共目录和接口文件由相关成员共同维护。修改公共文件前，应在群组或任务看板中说明影响范围。

## 四、Git 分支规则

### 分支结构

```text
main                         # 最终验收和发布版本
└─ develop                   # 日常集成和联调版本
   ├─ feature/player-miniapp
   ├─ feature/admin-web
   ├─ feature/game-engine
   └─ feature/platform-server
```

### 开发流程

1. 从最新的 `develop` 创建个人功能分支。
2. 只修改自己职责范围内的代码。
3. 一个提交尽量只完成一个相对完整的功能。
4. 在本地完成启动、编译和基础操作检查。
5. 将个人分支推送到远程仓库。
6. 提交 Pull Request，目标分支为 `develop`。
7. 由其他技术成员进行代码检查后合并。
8. 合并后所有成员同步 `develop` 并进行联调。
9. 联调通过后，由项目负责人将 `develop` 合并到 `main`。
10. `main` 只用于最终验收和发布，不直接开发功能。

### 分支命名

```text
feature/<功能名>              # 新功能
fix/<问题名>                  # 缺陷修复
refactor/<模块名>             # 重构
```

示例：

```text
feature/player-room-lobby
feature/game-vote-flow
fix/reconnect-room-state
```

## 五、跨分支协作规则

### 接口先行

成员3和成员4先确定服务端接口、数据库字段和实时消息格式；成员1和成员2依据接口文档开发页面，不自行猜测字段名称和返回结构。

接口至少要写清：

- 请求方法和路径
- 请求参数
- 返回字段
- 错误码
- 登录要求
- 权限要求
- 空值和重复提交规则

### 游戏状态先行

游戏引擎需要先定义房间状态，例如：

```text
WAITING
→ READY
→ PLAYING
→ ANSWERING
→ VOTING
→ FINISHED
```

每个状态都要说明：

- 谁可以触发状态变化
- 状态变化的条件
- 玩家端显示什么
- 允许哪些操作
- 异常或超时如何处理

### 内容格式统一

内容组提供剧本时，至少要包含：

- 剧本基本信息
- 支持人数
- 角色列表
- 章节列表
- 公共剧情
- 私密线索及发放对象
- 任务和答案
- 投票选项
- 结局条件

成员2负责把这些内容录入后台，成员3负责让游戏引擎能够读取并执行这些配置。

## 六、开发和联调顺序

建议按以下顺序推进：

1. 成员4完成项目基础环境、数据库、登录和基础接口。
2. 成员3完成房间系统和游戏状态机。
3. 成员1完成登录、创建房间、加入房间和游戏页面。
4. 成员2完成剧本配置后台。
5. 成员3和成员4联调游戏接口和实时通信。
6. 成员1和成员3联调玩家端完整游戏流程。
7. 成员2和成员3联调剧本配置、章节推进和结局规则。
8. 四人共同在 `develop` 上跑通完整流程。
9. 稳定版本合并到 `main`，交由项目验收人员验收。

完整流程必须能够实际跑通：

```text
登录
→ 创建房间
→ 多人加入
→ 开始游戏
→ 自动分配角色
→ 阅读剧情
→ 查看私密线索
→ 完成任务
→ 答题或投票
→ 自动结算
→ 查看结局
```

## 七、完成标准

一个功能只有同时满足以下条件，才算完成：

- 代码已经提交到个人功能分支。
- 本地可以启动或编译。
- 已接入约定的接口或数据格式。
- 已处理加载、空数据、重复操作和错误提示。
- 已在 Pull Request 中写明修改内容和验证步骤。
- 已通过至少一名其他技术成员的代码检查。
- 合并到 `develop` 后没有破坏已有流程。

## 八、禁止事项

- 不直接在 `main` 上开发。
- 不把密钥、密码、真实用户数据提交到仓库。
- 不在前端单独实现关键游戏规则。
- 不未经沟通修改其他成员负责的核心文件。
- 不随意修改已经约定的接口字段。
- 不把临时测试数据和生成文件放入正式源码目录。
- 不以“代码能编译”代替完整流程联调。

## 九、当前待确认事项

正式开发前，技术组需要共同确定：

1. 微信小程序原生开发还是使用跨端框架。
2. 后端语言和框架。
3. 云服务器、数据库和对象存储方案。
4. WebSocket 或其他实时通信方案。
5. 房间最大人数和预计并发量。
6. 剧本数据格式和结局条件表达方式。
7. `main`、`develop` 和远程仓库的实际创建人。
